# 算力集市 · 后续开发路线图

版本：2026-10-29。下方里程碑正文保留最初规划，最新现状见文末“开发进度补记”。当前已完成本机受邀工作台、PyTorch CUDA 和跨单文件恢复，独立机主与公网运营仍未验收；计费规则不变。

## 目标与现状

下一次完整交付的目标：机主接入一台机器 → 上架真实可用的 GPU → 租客下单 → 浏览器打开工作环境 → 运行 GPU 示例 → 结束租用 → 容器销毁、释放资源、按规则结算。

当前已具备：React/Express/SQLite 应用，注册登录、模拟挂牌、预付、按秒计费、提前结束、到期结算、钱包流水。已有 15 个单元/接口测试与 1 个双会话端到端测试的通过记录。此次规划阅读了现有代码与验收文档，没有重新执行测试。

当前缺少：实际硬件校验、逐卡分配、agent 注册与心跳、可靠任务下发、容器执行、远程访问、掉线失败退款、机主管理页面、最小运营后台、生产运行方案。

技术路线延续现有栈：先保留 Express、SQLite 和 React；控制面增加 WebSocket 与持久化任务记录；agent 使用 Node/TypeScript CLI，构建为可执行的 JS 包。第一版先单控制面实例，不引入分布式调度或 Kubernetes。

## 里程碑 A：整理地基，阶段 1.1

目的：为接机做好结构准备，同时保留现有交易演示。

开发内容：

- 将 server/app.ts 按 auth、listings、orders、wallet、machines 拆成路由与服务；拆分前端页面、弹窗、API 类型。拆分只改变组织，不改交易行为。
- 增加版本化数据库迁移；升级前备份，迁移失败停止启动，不直接覆盖旧数据库。
- 明确 demo/connected 两类资源和运行模式；模拟机器不能被当成真实库存。真实接入模式下，一键演示额度不能兑换真实机器使用权。
- 下单引入请求幂等键，防止重试创建两个订单或重复预付。现有结束订单幂等继续保留。
- 补真实进程重启、定时器触发、异常事务回滚、注册并发冲突的测试；已有的文件关闭重开测试继续保留。
- 记录请求 ID、订单 ID 和操作事件；日志屏蔽密码与凭据；增加健康检查与备份恢复脚本。

验收：旧演示完整可用；数据库迁移前后余额与流水一致；重复提交只生成一单；杀进程再启动能恢复到期结算；备份可恢复到单独目录。

## 里程碑 B：无卡也能开发，阶段 2a / mock agent

目的：把真实接机需要的通信和状态流程跑通。

开发内容：

1. **机主管理**：新增“我的机器”，可创建设备接入凭据、查看最近心跳、硬件信息、状态和停用原因。凭据只展示一次，控制面只存哈希，可撤销和轮换。
2. **agent CLI**：注册、每 10 秒心跳、上报模拟 GPU UUID，接收启动/停止命令，上报状态和日志；模拟器可配置启动失败、延迟、掉线和重复回报。
3. **逐卡库存**：按 GPU UUID 记录设备；机器挂牌只能引用该机主已接入的卡。下单预留具体卡位，避免同一张卡被多张挂牌重复出租。
4. **任务下发**：持久化启动/停止任务，包含唯一任务 ID、订单 ID、租约版本、截止时间；断线重连后可以重放，agent 对重复命令只执行一次。最多重试启动 1 次。
5. **订单进度**：前端显示“正在分配 / 准备环境 / 可进入 / 正在清理 / 已结束 / 失败原因”，暂不伪装成真实终端。
6. **失败退款**：启动失败、准备超时、运行中机器失联，按交接包规定全额退回该单预付；失败订单不产生机主收入。所有退款走统一事务和唯一业务标识，禁止重复退款。

建议新增表：

- schema_migrations：数据库版本。
- machine_gpus：机器、GPU UUID、型号、显存、可用状态。
- agent_credentials：凭据哈希、关联机器、过期/撤销时间。
- gpu_allocations：订单与具体 GPU 的预留、占用、清理和租约状态。
- agent_jobs：启动/停止命令、投递次数、超时、执行结果。
- order_events：进度、失败原因与追踪记录。
- order_requests：租客请求幂等键、请求摘要和结果订单 ID。

先给现有 orders 增加 execution_status、ready_at、failure_code 等字段；交易状态仍保留 running/finished/failed，避免立刻推翻现有接口。结算状态与资源是否清理分别记录，不能把“已退款”当成“卡已可再次出租”。

建议接口：

- 用户端：GET /api/machines/mine；POST /api/machines；POST /api/machines/:id/credentials；POST /api/machines/:id/disable。
- agent：注册、认证 WebSocket、心跳、任务领取/回报、受限日志上传。
- 订单：GET /api/orders/:id/events；查询分配及清理进度。
- 具体接口路径在实施时固定到 docs/agent-protocol.md，客户端与服务端共用 zod 消息定义。

验收：无 GPU 的本机可启动两个 mock agent；完成正常租用和结束流程；重启控制面后恢复任务；重复回报不重复扣款/退款；乱序启动命令不能复活已取消订单；启动失败/心跳超时自动全额退款；失联库存立即停止新租用。

## 里程碑 C：单台真实 GPU，阶段 2b

目的：把 mock 执行器换成真实 Docker 执行器，控制面协议不变。

第一台优先使用可控的 Linux + NVIDIA 主机；Windows 作为兼容路线，通过 WSL2 与 Docker Desktop 的 GPU 支持验证后再纳入承诺。开发机器没有 GPU 不影响里程碑 A、B。

开发内容：

- 接机前采集系统、驱动、Docker、GPU UUID/显存、可用磁盘与网络连通性；提供诊断命令和失败说明。
- nvidia-smi 校验真实硬件；每单独占整张 GPU，不先做显存切分、MIG 或跨机器多卡。
- 只允许平台维护的固定镜像，镜像固定摘要；先用 CUDA/Python 验证镜像，再加 JupyterLab。
- 用订单 ID 与任务 ID 命名和标记容器，绑定指定 GPU UUID，限制 CPU、内存、磁盘和最大运行时间。
- 禁止租客提交宿主机命令、挂载 Docker socket、使用 privileged 容器或访问其他订单目录；agent 是受控宿主组件，安装权限需机主理解。
- 每单独立工作目录。容器退出、清理失败、残留文件都有状态和日志；结果文件保留策略必须向用户显示。
- 在线情况下结束/到期后 10 秒内销毁容器；失联时由 agent 本地租约看门狗停止过期任务。控制面禁止对尚未确认清理的卡重新派单。

验收：真实容器运行 GPU 示例，能验证分配的设备标识；其他 GPU 不对该容器开放；两个订单不能占同一张卡；结束后容器消失；杀 agent、断网、重启 Docker 后可恢复并清理残留。

重要边界：控制面无法在网络断开时保证远程机器“10 秒内收到销毁命令”。因此必须分别验收服务端停租/退款、本地租约过期停机、重新联网后的对账清理，而不是仅靠发一条停止消息。

## 里程碑 D：用户能真正用起来，阶段 2c / 工作台

目的：让租客从订单页直接进入可用环境。

开发内容：

- 订单详情展示准备进度、GPU、剩余时长、日志与“打开工作台”。
- 先完成 JupyterLab 的基础路径；为满足原始阶段 2 验收，再接浏览器终端（xterm.js + 受权限约束的终端代理），先不增加公网 SSH。
- agent 主动连接控制面中继，HTTP 与 WebSocket 流量沿反向连接代理；机主无需配置公网端口。
- 访问票据绑定用户、订单和服务，短期有效、单次兑换为访问会话；访问会话有明确有效期，每次建立连接核验订单状态。
- 到期、退款或机主停用后主动断开访问连接并禁止重新连接；Jupyter 内部认证仍保留，内部令牌不写入公共日志。
- 最小文件功能：上传脚本、查看运行结果、下载文件。明确容量、单文件大小、保留时间；原始阶段 2 未规定的具体数值实施前写入配置决策。
- 清楚区分“结束租用”和“保存结果”；不承诺容器销毁后数据仍永久存在。

新增 access_tokens/access_sessions 等访问记录；大文件先使用每单隔离目录，达到持久化和多节点需求后再接对象存储。

验收：外网另一台电脑能登录平台，进入正确订单的工作台，运行并下载 GPU 示例结果；不能打开其他租客的会话；订单结束后旧链接和已建立连接均失效；断线重连、访问票据复用与文件越权有测试。

## 里程碑 E：小范围可运营内测

目的：用少量可控机主和真实任务验证可靠性，仍可使用测试结算，不急于接真实支付。

开发内容：

- 最小管理员页面：机器健康、异常订单、失败原因、未清理资源、退款记录与平台服务费汇总。
- 管理员接口服务端鉴权与操作审计；管理员不能直接改钱包数字，需要有原因、有流水的业务操作。
- 只邀请熟悉的机主；远程代码执行、网络滥用与容器逃逸仍需专门审查，Docker 运行成功不等于可以开放陌生人共享宿主机。
- 用专用测试名额控制真实 GPU 成本；新用户赠送的虚拟 ¥100 不自动变成可消耗真实资源的信用额度。
- 增加运行监控：订单启动成功率、环境准备耗时、清理延迟、断线次数、退款率；每项都能追溯到订单日志。
- 支持服务进程守护、HTTPS、稳定公网地址、数据库定时备份、恢复演练和部署回滚。具体托管资源等有机器与网络预算后再选。
- 跑一轮完整生命周期与故障演练，记清系统能力和外部依赖，不用单纯“页面能打开”作为上线门槛。

建议内测样本：先 1 台真实 GPU 验证技术闭环，再邀请 3–5 位机主和约 10 位需求方。这是试验规模建议，不是已经具备的资源。

验收：样本订单能完整追踪；资金账本守恒；没有重复占卡、重复退款和遗留运行容器；人工能解释和恢复异常订单；能从备份恢复。

## 里程碑 F：场景产品与真实支付，阶段 3

先看内测用户真实在做什么，再选一个场景。候选是图像创作、Notebook 实验或模型微调；不同时建设三套产品。

- 场景模板：固定环境、依赖、示例任务、结果说明，减少用户自己装环境的步骤。
- 任务执行：上传输入→排队→执行→查看进度→下载结果；增加配额、取消、超时、重试与结果存储。
- 断点续跑只支持能够保存/恢复状态的具体任务，不承诺所有程序都可自动恢复。
- 真实支付作为独立工作包：根据商户资质和选定支付服务商核验能力，再开发支付通知验签、幂等、退款、分账、对账、结算与发票流程。
- 严格分离演示额度、测试配额与真实资金账；不把现有余额表直接当作可充值可提现钱包。
- 拼单、可中断实例、动态定价和推荐系统放在可量化需求出现后。

验收：选定场景至少有一个从输入到结果的真实任务；费用规则可解释、失败可恢复；支付先沙箱验证，真实资金上线前再核验资质及接入条件。本文不提供未经核验的法律或支付资质结论。

## 跨阶段必须先确定的规则

### 1. 启动等待是否计费

现有约定为创建订单即计时。接入真机后环境准备可能较慢。

建议：下单时只预付与预留，环境 ready 后设置计费起点和租用到期时间；准备失败全额退回，等待时间不占用户购买的工作时长。**这是计费规则变更提案，实施前需要用户明确确认并更新主需求文档。确认前仍按现有规则，不默默改价或改起算时间。**

### 2. 断线阈值与销毁目标

保留 10 秒心跳、30 秒无心跳判定掉线的目标。掉线扫描建议每秒执行，验收写成“最后心跳后 30 秒达到阈值，额外调度延迟在测试容差内”；不把检测任务本身也设为 30 秒一次。

掉线后停新单、失败退款、禁用访问；卡位转为待清理/隔离。仅在清理回报或可信恢复检查完成后解除隔离，不能为了库存数字好看直接释放。

### 3. 结束与失败的竞争

到期、用户结束、机器失联可能同时发生。通过单一结算服务、状态条件更新和唯一退款标识决定唯一终态；已完成的终态不因迟到心跳被重写，异常争议进入人工复核。

### 4. 服务故障与 agent 独立行为

命令按至少一次投递设计，执行必须幂等；订单取消先写入持久化状态再派发停止任务。agent 在断网时不能无限续租，必须服从已签发租约截止时间与本地看门狗。机器恢复后先对账，再接受新工作。

## 工作量估计与外部依赖

以下仅为单人开发的初步有效工作日估计，不是交付承诺；需要边开发边修订，不包含寻找机主、硬件采购、网络审批、资质申请与等待时间：

- A：整理地基，约 2–3 天。
- B：mock 协议闭环，约 3–5 天。
- C：单机 GPU 与容器生命周期，约 4–7 天，需要一台受控 NVIDIA 主机。
- D：工作台与反向访问，约 4–7 天，需要可从外网访问的控制面与浏览器验证环境。
- E：内测运营准备，约 3–5 天，取决于故障演练反馈。
- F：暂不承诺工期，待选定任务场景、支付服务商及资质后再拆分。

A–E 合计约 16–27 个有效工作日，实际日历周期会受机器与网络条件影响。优先交付可验收切片，不按估计时间跳过验收。
